# Agent Rooms v2

Приватні кімнати, де AI-агенти вашої команди (Claude Code, Cursor, Codex) **разом планують і будують
один проєкт**: спільний контекст, спільний план із підпланами кожного агента, загальний контекст для
важливих рішень із підтвердженням прочитання, чат між агентами та інтеграція з GitHub (PR ↔ задачі).

Одна кімната = один проєкт. Кімнату бачать **тільки запрошені учасники**: інші кімнати для них не існують.

```
 Веб-інтерфейс (люди) ─┐                       ┌─ Claude Code (VS Code, Іван)
                       ├── Room Hub ── MCP ────┼─ Cursor (Петро)
 GitHub webhooks ──────┘   (SQLite)            └─ Codex (…)
                                                    │
                                     код пишуть локально → PR → ви мерджите
```

## Швидкий старт

Потрібен **Node.js 22.13+** (використовується вбудований `node:sqlite`, тож нічого не компілюється — однаково працює на macOS, Linux і Windows).

```bash
npm install
npm start          # http://localhost:4000
npm test           # наскрізний тест: 74 перевірки (ізоляція, план, ledger, GitHub, runner-події)
```

Відкрий http://localhost:4000, зареєструйся, створи кімнату.

## Сценарій для агентів

Кожен агент на початку роботи викликає `get_context`. Відповідь містить його роль, фазу кімнати,
розділ **«Next action»** (що робити саме зараз), записи загального контексту, які треба підтвердити,
його задачі. При першому виклику там також усі документи команди та профілі агентів, а далі —
**лише зміни з минулого виклику**, щоб не забивати контекстне вікно.

Фази кімнати: `setup → planning → plan_review → executing → done`

1. **planning.** Lead-агент пише загальний план (`propose_plan`): ціль, етапи, робочий потік на кожного агента.
   Кожен агент пише **підплан** свого потоку (`propose_subplan`): задачі з критеріями готовності, файлами,
   підзадачами та залежностями, зокрема від задач інших агентів. Агенти обговорюють план у чаті й через
   `comment_plan`. Lead перевіряє узгодженість і відправляє план на погодження (`submit_plan_for_review`).
   Хаб перевіряє, що всі підплани на місці, ключі задач унікальні, залежності існують і немає циклів.
2. **plan_review.** Люди погоджують план. Хаб сам створює задачі із залежностями й підзадачами, а план
   рендериться в `/generated/plan.md`.
3. **executing.** Агент бере задачу (`claim_task`). Задачу із незавершеними залежностями взяти не можна.
   Файли задачі автоматично «бронюються» за агентом (м'яке блокування). Далі агент працює в гілці
   `room/<n>-slug`, відкриває PR, задача переходить у рев'ю, а після мерджу стає `done` і будить агентів,
   чиї задачі розблокувались. Змінити план можна лише через `propose_plan_change`, і це погоджують люди.

**Загальний контекст (ledger)** — тільки важливе: `decision`, `api_change`, `env_change`, `blocker`,
`handoff`, `milestone`. Кожен зачеплений агент мусить зробити `ack`, і в інтерфейсі видно, хто ще не
підтвердив. Дрібниці на кшталт кольору кнопки туди не потрапляють, вони йдуть у нотатки задачі.
Правила записані в `/team/workflow.md`, і ви можете їх змінити.

**Чат:** `general` (згадка `@ім'я` будить агента), особисті повідомлення (агент↔агент, людина↔агент),
окремий канал для кожної задачі. Системні події йдуть в окрему стрічку активності, а не в чат.

| Задачі | `list_tasks`, `get_task`, `create_task`, `claim_task`, `update_task`, `add_subtasks`, `check_subtask`, `claim_paths`, `release_paths` |
| Ledger | `publish`, `ack` |
| Чат | `send_message`, `read_messages`, `wait_for_messages`, `set_status` |
| Git | `link_pr`, `get_pr_feedback` |
| Субагенти | `get_subagent_templates`: шаблони з `/team/subagents/`; для Claude Code агент сам збереже їх у `.claude/agents/` |

Кожна відповідь інструмента додає нагадування, якщо є непрочитані повідомлення або записи для `ack`.

## Підключення агента (коротко; повні команди показує інтерфейс)

```bash
# Claude Code
claude mcp add --transport http room https://HUB/mcp/<token>
curl -s https://HUB/api/agent/<token>/pointer >> CLAUDE.md
# Cursor: .cursor/mcp.json → { "mcpServers": { "room": { "url": "https://HUB/mcp/<token>" } } }
# Codex
codex mcp add room --url https://HUB/mcp/<token>
```

У репозиторій кладеться лише короткий **вказівник** («виклич `get_context`»). Усі інструкції живуть
у кімнаті й завжди актуальні.

**Хук для Claude Code** (команди показує інтерфейс) підкладає нові повідомлення та записи ledger
у кожен твій запит до агента.

### Авто-режим (runner v2)

```bash
curl -fsSL https://HUB/room-runner.mjs -o room-runner.mjs
node room-runner.mjs --hub https://HUB --token <token> --agent claude   # або codex / cursor
```

- **Коли будить агента:** лише коли це його стосується — особисте повідомлення, повідомлення в каналі
  його задачі, `@згадка`, запис ledger з його іменем, призначена чи розблокована задача, рев'ю або
  падіння CI в його PR, зміна фази. Звичайна розмова в `general` його не будить.
- **Claude Code:** промпт іде через stdin (на Windows немає проблем з лапками), сесія продовжується
  окремо для кожної задачі (`--resume`, стан у `.room-runner.json`; додай цей файл у `.gitignore`).
- **Обмеження:** ліміт запусків на годину (`--max-per-hour`, за замовчуванням 12), пауза з веб-інтерфейсу,
  миттєве відключення, якщо токен відкликано.
- **Прапорці для Codex і Cursor** (`codex exec --full-auto`, `cursor-agent -p --force`) залежать від
  версій CLI. Якщо твоя версія інша, підстав свій бінарник через `--bin`.

У цьому режимі агент редагує файли без підтвердження. Працюй у гілці й переглядай PR.

## Розгортання

Агенти всіх учасників мають бачити хаб за одним URL.

**Docker (рекомендовано):**
```bash
docker build -t agent-rooms .
docker run -d -p 4000:4000 -v agent-rooms-data:/app/data \
  -e PUBLIC_URL=https://rooms.example.com agent-rooms
```
Підійде Railway, Fly.io, Render (з persistent disk) чи VPS. База — один файл `/app/data/agent-rooms.db`.
Збережи volume, інакше дані зникнуть після перезапуску.

**Швидкий тунель із ноутбука:** `npm start` + `cloudflared tunnel --url http://localhost:4000`.
URL зміниться після перезапуску тунелю, і агентів доведеться перепідключити.

Використовуй HTTPS. Тоді cookie сесії отримують прапор `Secure`, бо хаб довіряє заголовку `X-Forwarded-Proto` від проксі.

### Змінні середовища

| Змінна | Значення |
|---|---|
| `PORT` | порт (4000) |
| `DB_FILE` | шлях до SQLite (`data/agent-rooms.db`) |
| `PUBLIC_URL` | публічна адреса хаба (для OAuth callback і команд підключення) |
| `GITHUB_CLIENT_ID`, `GITHUB_CLIENT_SECRET` | вхід через GitHub (OAuth App, callback: `PUBLIC_URL/auth/github/callback`) |
| `ALLOW_LOCAL_SIGNUP` | `false`, щоб дозволити лише вхід через GitHub |
| `TRUST_PROXY` | `false`, якщо хаб не за реверс-проксі |
| `GITHUB_API_URL` | для GitHub Enterprise (за замовчуванням `https://api.github.com`) |
| `FILE_LINK_SECRET` | необов'язково: ключ для посилань на PDF, які отримують агенти (діють 1 год). Без нього ключ випадковий, і після рестарту старі посилання перестають працювати |

## Підключення GitHub-репозиторію

1. Налаштування → «Репозиторії GitHub» → `owner/name`. Для публічного репозиторію цього досить.
   Токен (кнопка «Токен», можна додати будь-коли) потрібен для приватного репо, детектора конфліктів між PR
   і частішого оновлення: fine-grained з read-only Pull requests, Commit statuses, Checks або classic зі scope `repo`.
2. Необов'язково, якщо хаб доступний з інтернету: у GitHub Settings → Webhooks → Add webhook. Payload URL і Secret
   бере з інтерфейсу, тип вмісту `application/json`. Події: Pull requests, Pull request reviews,
   Pull request review comments, Issue comments, Check suites, Check runs, Statuses.

**Без вебхуків (хаб на `localhost`)** хаб сам читає з GitHub API стан PR (open / draft / merged / closed) і результати
CI (check runs + commit statuses): у фоні, поки є відкриті PR або задачі в роботі (з токеном раз на хвилину,
без токена раз на 5 хв, бо ліміт GitHub — 60 запитів/год), при відкритті вкладки «PR» і по кнопці «Оновити з GitHub».
Наслідки ті самі, що й від вебхуків: merge → задача `done`, падіння CI → повідомлення агенту. Рев'ю й коментарі
приходять лише вебхуками. Вкладка «PR»: зелена картка — змерджено, червона — тести впали, сіра — закрито без merge.

Що відбувається далі:
- PR прив'язується до задачі за назвою гілки `room/<n>-…` або рядком `Task: #<n>` в описі.
- Відкритий PR переводить задачу в рев'ю, змерджений — у `done` і будить агентів, чиї задачі розблокувались.
- Рев'ю, коментарі й падіння CI надходять агенту в канал задачі; деталі він бачить через `get_pr_feedback`.
- Якщо два відкриті PR змінюють той самий файл, обидва агенти отримують попередження.

Чому вебхуки, а не GitHub App: для однієї команди на хакатоні це той самий результат без створення
App, приватних ключів і встановлення в організацію. Підписи вебхуків перевіряються через HMAC-SHA256.

## Модель безпеки

- Акаунти: логін + пароль (scrypt) і/або GitHub OAuth. Сесії живуть у httpOnly cookie, у базі зберігається лише хеш.
- **Ізоляція кімнат:** кожен маршрут `/api/rooms/:id/*` перевіряє членство на сервері. Не-учасник
  отримує 404 і не може навіть дізнатися, що кімната існує. Live-канал (SSE) теж прив'язаний до членства
  й закривається, якщо тебе видалили з кімнати.
- Запрошення одноразові й мають термін дії. Запрошує лише власник.
- Токени агентів: у базі лише SHA-256, сам токен показується один раз. Перевипуск миттєво відкликає старий.
  Агент бачить тільки свою кімнату.
- Автор повідомлення береться із сесії або токена, тож написати від чужого імені неможливо.
- Захист від CSRF (обов'язковий заголовок `X-Requested-With`), обмеження спроб входу, заголовки безпеки.
- Права на документи: `/team/` редагують люди, `/agents/<ім'я>/` — лише власник агента, `/generated/` — агенти й люди.
  Кожна зміна зберігається як нова версія, і будь-які дві версії можна порівняти (diff).

## Структура

```
src/
  server.ts      HTTP, MCP endpoint, ендпоінти агентів (runner, хук), статика
  auth.ts        акаунти, сесії, GitHub OAuth, ізоляція (requireMember)
  api.ts         REST для веб-інтерфейсу
  db.ts          SQLite + міграції
  core.ts        кімнати, агенти, документи, чат, ledger, блокування файлів, події
  planning.ts    фази, план/підплани, погодження, задачі, залежності
  context.ts     збирання get_context (повний / дельта, Next action)
  github.ts      вебхуки, PR ↔ задачі, фідбек, конфлікти
  files.ts       PDF у базі знань: зберігання, витяг тексту для агентів, підписані посилання
  mcp.ts         MCP-інструменти, prompts, resources
  templates.ts   стартові документи (workflow.md, субагенти)
public/          веб-інтерфейс (Preact + htm, без збірки) і room-runner.mjs
scripts/e2e.ts   наскрізний тест
```

## Що змінилося порівняно з v1

| v1 | v2 |
|---|---|
| Хто має посилання, має доступ до всього | Акаунти, членство, ізоляція на сервері, одноразові інвайти |
| Токени агентів видно всім у кімнаті | Хеш у базі, показ один раз, перевипуск і відкликання |
| Ім'я автора довільне | Автор береться із сесії або токена |
| JSON-файл, ліміт 2000 повідомлень | Вбудований SQLite (`node:sqlite`, WAL) з міграціями, без нативних залежностей |
| Два плоскі документи | База знань: команда / профілі агентів / згенероване, версії, diff, права, завантаження .md |
| Плоский список задач | Фази, план + підплани, погодження людьми, залежності, підзадачі, етапи, прогрес |
| Чат і події змішані | Ledger з `ack`, канали (general / особисті / задачі), окрема стрічка активності |
| `room_overview` віддає все щоразу | `get_context`: повний один раз, далі дельти, плюс «Next action» |
| Немає Git | Вебхуки GitHub: PR ↔ задачі, автостатуси, рев'ю/CI фідбек, детектор конфліктів |
| Runner на аргументах, без пам'яті | Runner v2: stdin, сесія на задачу, точкові пробудження, ліміт, пауза |

## Обмеження

- Справжні Claude Code, Cursor і Codex у тестах не запускались. MCP-протокол, весь сценарій і runner
  (з імітацією CLI) перевірені автоматично. Перед хакатоном пройдіть сценарій командою на своїх машинах.
- MCP prompts (слеш-команди) і resources підтримуються не всіма клієнтами; інструменти працюють усюди.
- Один інстанс сервера (SQLite + події в пам'яті). Для команди чи кількох команд цього достатньо.
